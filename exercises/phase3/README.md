# Phase 3 — Programmatic GIS

Start at [the guided path](../../index.html#phase3). Work through the four tasks in order, using the same synthetic districts, flood zone, clinics and raster. The site never executes Python, SQL or network requests. Completion is self-reported, not an execution result.

## Environment

Use a consistent conda-forge environment, for example:

```bash
mamba create -n pgis -c conda-forge python=3.12 numpy geopandas pyogrio shapely pyproj rasterio networkx pytest
mamba activate pgis
```

Optional note examples also require rioxarray, xarray, Dask, geopy, requests or a GDAL CLI installation. No online service is needed for the four core exercises. Use the provider's current policy if you try the HTTP examples. SQL requires a separate PostGIS/pgRouting database; it creates tables and is intended for a disposable database.

## Try first, then compare

Download `exercise-1.md` through `exercise-4.md` for the original tasks, prerequisites, inputs and success criteria. Write your own `fixtures.py`, `vector_ops.py`, `raster_ops.py`, `scale_demo.py` and `capstone.py` in a new local folder. Keep original inputs separate from generated GeoPackages, rasters and reports. The expected output filenames are generated by your local runs; they are not supplied as fabricated evidence.

`solutions/` contains complete source solutions, not unimplemented starters. `fixtures.py` combines the Solution 1 fixtures and Solution 4's `make_roads()` addition. All other code blocks are preserved as supplied. Read the separate clarifications on the website before running. Copy all needed modules into the same new local folder, then run:

```bash
python check_ex1.py
python -m pytest test_vector_ops.py
python raster_ops.py
python scale_demo.py
python capstone.py
```

These commands create `ex1.gpkg`, `elev.tif`, `risk.tif`, `capstone_results.gpkg` and the initial `capstone_report.md` in the current directory. They may overwrite earlier outputs. Add the required assumptions and limitations to the capstone report: the source writer supplies only its summary table. Record actual results, tool versions and any mismatch instead of assuming these commands pass in every environment.

`flood_exposure.py` is the complete Section 5 worked example. `javascript-examples.mjs` is the source JavaScript listing, not a standalone offline test: install proj4, @turf/turf and geotiff separately and replace its placeholder raster URL before using it.

## Important source limitations

- `TransformerGroup` is imported from `pyproj.transformer`, not top-level `pyproj` (Section 4.2).
- A projected CRS is not necessarily metric. These fixtures use EPSG:32631 in metres.
- Geometry `.buffer()` and top-level `shapely.buffer()` have different default resolutions. GeoPandas's 16 segments per quadrant produces the expected 64-gon areas; set `resolution=16` explicitly when reproducing them.
- The raster solution is for an all-valid, north-up fixture. Generalise with masked reads, class 0 for missing cells and float64 accumulation, then test missing-data and multi-block rasters. The tiny fixture may occupy just one native block.
- The closure rule is **positive flooded length**, not every point touch. The service-area result is a set of reachable vertices, not an isochrone polygon.
- District B's 6000 residents are the isolated clinic's host population, not a measured number of residents cut off.
- Source solutions are retained for comparison, not silently corrected or certified as executed. Build and browser/content tests establish inclusion and UI behaviour, not native GIS or external-service correctness.
